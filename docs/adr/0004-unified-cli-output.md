# ADR 0004：统一 CLI 输出层

- 状态：已接受
- 日期：2026-07-19

## 背景

当前 CLI 已统一使用 Cobra 构建命令树，并约定正常结果写入 stdout、诊断和错误写入
stderr，以及成功、运行失败、使用错误和部分成功的退出码。然而，各命令分别组织输出，
形成了表格、JSON、JSONL、`key=value`、裸路径、自然语言和静默成功等多种不一致的
表现形式。

这种差异使交互用户难以判断命令是否成功、空结果意味着什么以及下一步应该做什么，
也使脚本调用方无法依赖统一、稳定的结构化输出契约。全局 `--format`、`--quiet`、
`--verbose` 和 `--no-color` 也缺少一致语义。

## 决策

CLI 使用统一输出层。业务逻辑只返回领域结果和错误，不直接决定终端展示；命令层描述
结果的业务含义；输出层统一处理格式选择、人类可读布局、机器可读编码、诊断、空状态、
批量结果和终端能力。

人类输出与机器输出使用独立契约。人类输出以清晰、可扫描和可操作为目标；机器输出以
稳定字段、明确版本和无非结构化内容混入为目标。终端是否为 TTY 只能影响布局、颜色和
进度，不得隐式改变数据格式。

每个叶命令必须明确声明支持的格式。默认格式面向人类阅读；JSON 用于可聚合的结构化
结果，JSONL 用于流式批量结果，CSV 只用于天然二维数据，Raw 用于必须原样消费的内容。
帮助只展示当前命令实际支持的格式。

成功命令必须输出业务结果或明确的空状态，不得使用空 stdout 表达“没有数据”。空状态
应说明当前状态，并在存在明确操作时给出下一步命令。修改型命令必须区分已修改、未变化、
已跳过、已取消和已调度等状态，不得静默成功。

dry-run 必须清楚描述将执行的动作、资源和目标，并明确说明没有产生变更。批量命令必须
标识每个输入的结果并提供汇总；现有退出码 `0`、`1`、`2` 和 `3` 的语义保持不变。

错误和警告使用稳定的领域诊断代码、用户可理解的消息以及可执行的修复建议。底层系统、
网络和解析错误不得未经转换直接成为默认用户输出。所有诊断都必须避免泄露令牌、密码、
许可证原文和包含认证信息的 URL。

## 输出通道与全局参数

人类模式下，正常结果、空状态和 dry-run 计划写入 stdout；错误、警告、进度和 verbose
诊断写入 stderr。进度只在适合交互显示时输出。

机器模式下，stdout 必须始终包含完整、有效的目标格式，不能混入提示、进度、颜色或
诊断文本；错误也必须提供稳定的机器可读结构。

全局参数采用以下统一语义：

- `--quiet` 保留业务结果、错误和重要安全警告，只隐藏进度、装饰信息和非必要诊断；
  不得整体丢弃 stdout。
- `--verbose` 增加有助于诊断的上下文，但不得泄露敏感信息。
- `--no-color` 关闭所有 ANSI 颜色；机器输出和 Raw 输出永不着色。
- `--format` 只能选择当前叶命令明确支持的格式。

## 影响

- 所有命令将共享一致的结果、空状态、诊断和格式语义。
- 业务逻辑与终端展示解耦，业务包不依赖 CLI 框架或输出格式。
- 部分现有默认文本和 JSON 结构会发生兼容性变化，需要明确管理机器输出版本和发布说明。
- 新命令必须遵循统一输出契约，不得创建私有输出风格。
- 输出行为需要覆盖 stdout、stderr、退出码、结构化格式有效性、终端适配和敏感信息安全。

## 未采用的方案

- 仅统一文案或封装格式化打印：无法约束空状态、机器格式、诊断和批量语义。
- 所有命令只输出 JSON：会降低交互可读性，也不适合帮助、安装计划和进度提示等自然
  文本场景。
- 根据是否连接 TTY 自动切换 JSON：会使同一命令的默认输出不稳定，不利于调试和脚本
  维护。
- 继续允许命令自行选择输出风格：维护成本和兼容性风险会随命令数量持续增长。
